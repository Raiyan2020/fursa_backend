## BE-14 — Volunteer attendance is counted, but Attended list and certificate are missing

**Done:**

1. **Attended-list contract.** `GET /list-user-opportunities/?filter_type=attended` is now a real, correctly-named value. It returns exactly the query that was already running under `filter_type=organized` on this endpoint (that name was a leftover misnomer — despite its name, `organized` here has never filtered by `created_by`; it already required a completed opportunity + at least one attended registration, i.e. it already *was* "attended" logic). Both `attended` and `organized` now run the identical query, so nothing that already relies on `organized` breaks. `registered` is unchanged and remains a strict superset (any registration, attendance or not) — the two are not disjoint; every `attended` row is also a `registered` row.
2. **Certificate support for `volunteer_opportunity` — built per your exact design:** as soon as the opportunity completes, every already-attended registration is issued a certificate and emailed immediately, hooked into `fursa:advance-statuses` right where it flips the status (mirroring how Learn&Serve's own auto-credit block already lives in that same command). 3. **Eligibility rule:** opportunity `opportunity_status = completed`, the registration has at least one `volunteer_opportunity_attendances` row with `is_attended = true`, and it isn't already certified. Hours printed on the certificate are the **sum of all attended attendance rows at issuance time** — so both the automatic pass and the manual "send" action always print final hours as of *when they run*, not a stale first value.
4. **Hours corrected after issuance:** re-running the manual "send certificates" endpoint does **not** currently re-render an already-issued certificate (it only processes rows that aren't certified yet) — so if hours are corrected after a certificate already went out, the printed PDF/HTML will still show the original number until we add an explicit re-issue path. This was left as designed rather than guessed — flagging so you know it's not yet handled, not silently broken. Say if you want re-issuance on correction and we'll add it (likely: clear `is_certified` when `total_hours` changes on an already-certified registration, so the next automatic/manual pass re-renders it).
5. **Retry-safe / no duplicates:** confirmed by test — the manual endpoint returns `certificates_sent: 0` on a second call with nothing new eligible, and `is_certified`/`certificate_image` are only ever set once per registration.
6. **Backfill:** `php artisan fursa:backfill-missing-volunteer-certificates` — a new one-time command (not a cron) covering every already-attended, completed, not-yet-certified `VolunteerOpportunityRegistration` that existed before this shipped, including registration **996**. **This still needs to actually run on the live database** — same caveat as the interest-tags backfill from yesterday, I don't have live DB access from here.
7. **Contract:** `GET /user-certificates/?user_id=` now returns rows from **both** registration types, unioned, in the exact shape you specified (`registration_id`, `certificate_image` as an absolute URL, `opportunity__title_en`, `opportunity__title_ar`, `organizer_name`) — no shape change, no MIME change; certificates are HTML (same as Learn&Serve's, not PDF), matching the existing pattern rather than introducing a second certificate format. `GET /download-certificate/?registration_id=996` now also resolves `VolunteerOpportunityRegistration` ids — since the two registration tables have independent id sequences, add `&registration_type=volunteer` (or `learn_serve`) when you already know which type a given id is, to avoid relying on the fallback-search order. Without it, the endpoint tries Learn&Serve first, then volunteer, which is correct as long as ids don't collide across the two tables (they can, in principle — pass the type when you have it).
8. **Attendance-id mismatch (765 vs 768) — not a bug.** Read `VolunteerAttendanceController::updateHours()` end-to-end: it does a strict `VolunteerOpportunityAttendance::query()->find($attendance_id)`. The far more likely explanation: a concurrent scan/manual check-in re-recorded attendance for that registration+day between when the frontend first read "765" and when it sent the `PATCH` — `AttendanceService::record()` (the scan/manual check-in path, not `updateHours` itself) looks up by `registration_id + attended_date` and can update-or-create, which would explain a stale client-side id being superseded by a fresh row. Worth checking your own capture's timestamps for a second check-in between the two requests; nothing on this side can substitute one attendance row for another.
