## BE-75 — The departure scan: a two-hour grace period after the session ends (volunteering only) ✅ Done

- [x] A. Enforce the deadline in `VolunteerAttendanceController::selfScan()`: refuse an `out` scan once `now()` passes the scheduled session end (per-day `time_slots` row if present, else the opportunity's `start_time`/`end_time`, with an overnight roll-over when end <= start) plus a grace period. Grace period must be a new `Config` row `self_check_out_grace_hours` (default 2), not a hardcoded constant.
- [x] B. Add `self_check_out_closes_at` (ISO-8601) to the attendance/opportunity payload while a check-out is pending, so the frontend (`selfCheckOutWindow.ts`) can stop deriving the deadline client-side.
- [x] C. Cap credited hours in `AttendanceService::selfCheckOut()` to the **overlap** between presence and the scheduled session — `max(checked_in_at, session_start)` to `min(checked_out_at, session_end)` — not the raw scan-to-scan difference. Clamp with `max(0, …)`. Keep the real `checked_out_at` as recorded (only `total_hours` is clamped). The organizer's manual `PATCH …/hours/` override stays uncapped, per the doc.
- [x] D. Fix the cross-midnight lookup bug: `selfScan()` currently finds the attendance row by `whereDate('attended_date', now()->toDateString())`, which fails for any session ending within the grace window of midnight (the check-in is filed under yesterday). Resolve the row from the most recent open check-in (`checked_in_at` set, `checked_out_at` null, session end + grace not yet passed) as a fallback when today's-date matching finds nothing. Also fix the `isWithinPreparationWindow()` call on the same path to use the resolved attendance's own date, not `now()`.

Implementation notes:
- New migration `2026_09_21_000001_add_self_check_out_grace_hours.php` adds `configs.self_check_out_grace_hours` (unsigned int, default 2); `Config::selfCheckOutGraceHours()` reads it with a `?? 2` fallback, mirroring `Config::platformFeePercentage()`.
- New `VolunteerOpportunity::sessionWindowForDate(string $date): ?array` resolves `['start' => Carbon, 'end' => Carbon]` for a given date — per-day `slotForDate()` first, else opportunity-wide `start_time`/`end_time`, with a next-day roll-over when `end <= start` (same resolution order as the existing `computeAttendanceHours()`). Returns `null` when the opportunity has no times set at all (kept the old uncapped/no-deadline behaviour for such opportunities, e.g. existing `SelfCheckInQrTest` fixtures).
- `VolunteerAttendanceController::selfScan()`: the attendance-row lookup now runs *before* the preparation-window check; for `direction === 'out'` with no usable same-day row, it falls back to the most recent open check-in (`checked_in_at` set, `checked_out_at` null) and re-derives `$attendanceDate` from that row's own `attended_date` — fixing both the cross-midnight lookup and the `isWithinPreparationWindow()` call. The grace-period deadline check runs only for `direction === 'out'`, after the already-checked-out/no-prior-check-in guards, and only when `sessionWindowForDate()` resolves a window.
- `AttendanceService::selfCheckOut()` now computes the overlap between `[checked_in_at, checked_out_at]` and the resolved session window via Carbon's `max()`/`min()`, using `floatDiffInHours($end, false)` (non-absolute) so a non-overlap clamps to 0 via `max(0, …)`. Falls back to the raw scan-to-scan difference when no window resolves (opportunity has no times set).
- `VolunteerAttendanceResource` gained `self_check_out_closes_at` (session end + grace, ISO-8601), `null` unless a check-out is currently pending (`checked_in_at` set, `checked_out_at` null) and a window resolves.
- `VolunteerAttendanceController::updateHours()` no longer caps at the opportunity's scheduled hours — the `$maxHoursForDay` check that used to sit in this action was removed. The doc is explicit and unambiguous on this (line 135-137 and the acceptance table's "organizer `PATCH …/hours/` with 6 | **6 is kept** — the cap is on self-scan only"), so this endpoint is now genuinely uncapped, matching the spec verbatim. `AttendanceService::selfCheckOut()`'s overlap-capping (part C above) is the only place hours get clamped for the self-scan path; the organizer's manual correction is untouched by it, as required.
- This removed a cap that had been added by an earlier, separate fix (`tests/Feature/AttendanceHoursCapTest.php`, "PDF review bug": manual attendance hours were being accepted up to a flat 24 regardless of the opportunity's real scheduled hours). That earlier fix's protection is **kept on the manual check-in endpoint** (`POST /volunteer-attendance/manual/`, still capped — the doc never asked to change that one) and **removed only from the hours-correction endpoint** (`PATCH …/hours/`), per this round's explicit instruction. `AttendanceHoursCapTest`'s corresponding test was updated (`test_update_hours_allows_a_correction_above_the_opportunitys_scheduled_hours`, renamed from `_rejects_`) to assert the new, spec-correct behavior — a 6h correction on a 4h opportunity is now accepted, not rejected.
- Tests: `tests/Feature/SelfCheckOutGraceWindowTest.php` (8 tests) — accept-within-grace + overlap capping, refuse-after-grace, configurable grace hours, `self_check_out_closes_at` exposure, cross-midnight fallback (accept and refuse cases), the client's worked 3.5h example, and the organizer-override-stays-uncapped case (6h correction on a 4h opportunity accepted). Full suite: 407 passed, same 1 pre-existing unrelated Postman-coverage failure as before this work — nothing else outstanding.

## BE-77 — `is_kuwaitis` becomes a four-way audience, and must block registration (⚠️ blocking) ✅ Done

- [x] A. Add `opportunity_nationality` (`all`/`kuwaitis`/`non_kuwaiti_arabic`/`non_arabic`, default `all`) to `volunteer_opportunities` and `learn_serve_opportunities`, backfilled losslessly from `is_kuwaitis` (`true → kuwaitis`, `false → all`). Keep accepting and returning `is_kuwaitis` for at least one release.
- [x] B. Decision (user, 2026-09-21): `users.speaks_arabic` (nullable boolean), `null` passes the filter. Built as specified.
- [x] C. Add the actual registration-blocking guard on both volunteer and Learn & Serve registration. Refusal message: "This opportunity is open to {audience} only." / "هذه الفرصة مخصصة لـ {audience} فقط." — same envelope shape as the existing age guard (`ApiResponse::error`, HTTP 400, `key: "fail"`).
- [x] D. Fix the `opportunity_nationality` list-filter query param to accept all four values (kept `non-kuwaitis` working as an alias for "not Kuwaitis-only").

Implementation notes:
- `volunteer_opportunities.opportunity_nationality` / `learn_serve_opportunities.opportunity_nationality` already existed as columns (from an earlier, unrelated 3-value `kuwaitis`/`all`/`other` scheme that nothing actually read — the list-filter bug in part D proves it was dead). New migration `2026_09_21_000002_add_be77_nationality_audience_fields.php` adds `users.speaks_arabic` (nullable boolean) and backfills every existing opportunity row's `opportunity_nationality` from `is_kuwaitis` (`true→kuwaitis`, `false→all`), overwriting whatever the column held before — per the doc, nothing else was expressible on the old boolean, so nothing is guessed.
- New `App\Enums\OpportunityNationality` (all/kuwaitis/non_kuwaiti_arabic/non_arabic) — kept separate from the existing `App\Enums\Nationality` (a *person's* own nationality: kuwaitis/other), since conflating "what a user is" with "what an opportunity targets" was the source of the old dead 3-value scheme. Carries `labelEn()`/`labelAr()` (used verbatim in the refusal message), `normalizeFields()` (keeps `opportunity_nationality` and legacy `is_kuwaitis` in sync — whichever the request actually sent wins, the other is derived), and `matches(?Nationality $userNationality, ?bool $speaksArabic)`.
- **Matching logic** (`OpportunityNationality::matches()`): a Kuwaiti is definitionally an Arabic speaker, so `nationality === kuwaitis` resolves the Arabic question too, regardless of the explicit `speaks_arabic` field — this is what makes "Kuwaiti user registers on a `non_arabic` opportunity → refused" hold even though `speaks_arabic` defaults to `null` (my first pass got this wrong and had to be corrected: unconditional null-passes would have let that case through). For everyone else, `null` on either signal (unanswered nationality or `speaks_arabic`) passes rather than blocks, per the user's decision.
- Registration guard (`HandlesOpportunities::rejectIfNationalityMismatch()`) wired into both `VolunteerOpportunityRegistrationController::createRegistration()` and `LearnServeRegistrationController::createRegistration()`, right after the duplicate-registration check.
- List filter fix centralized as `HandlesOpportunities::applyNationalityFilter()`, used by both the volunteer and Learn & Serve public list endpoints (previously each had its own copy of the same `kuwaitis`/`non-kuwaitis`-only bug). Now filters directly on `opportunity_nationality` (all 4 values) and keeps `non-kuwaitis` as an alias for `opportunity_nationality != 'kuwaitis'`.
- `speaks_arabic` wired into: `RegisterRequest`/`AuthService::register()` (individual signup), `VolunteerProfileUpdateRequest`/`VolunteerProfileController::update()` (volunteer profile edit), and `AuthController::updateAccount()` (account edit) — exposed back on `AccountResource` and `VolunteerProfileResource`. Admin user management (`Admin/UserController.php`) was left untouched — out of scope per the doc, which frames this as a signup/profile change only.
- Both API opportunity controllers (`VolunteerOpportunityController`, `LearnServeOpportunityController`) and their Admin dashboard counterparts now validate `opportunity_nationality` against the new enum and call `OpportunityNationality::normalizeFields()` on create/update; the admin Blade forms' nationality field now render the 4 new options (the Learn & Serve one was a free-text input before — converted to a `<select>` to match the volunteer form and the new `Rule::in` constraint).
- Tests: new `tests/Feature/OpportunityNationalityAudienceTest.php` (9 tests) — column A behavior (store/return, legacy `is_kuwaitis` compat, default `all`), the list filter (all 4 values + legacy alias), and the registration guard across the acceptance table's key rows (Kuwaiti on `kuwaitis` → allowed, Kuwaiti on `non_arabic` → refused, unanswered `speaks_arabic` passes `non_kuwaiti_arabic`, explicit non-Arabic-speaker refused, same guard on Learn & Serve). Full suite: 400 passed, same 1 pre-existing unrelated Postman-coverage failure as before this work.
